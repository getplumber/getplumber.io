**In one line:** the average public pipeline scores a D, only 3% come back clean, and none of it requires a zero-day to exploit.

## How we graded it

- **[Plumber Radar](/radar)** continuously scans public GitHub and GitLab projects.
- Each one is analysed by the open-source [Plumber CLI](https://github.com/getplumber/plumber), which reads the pipeline configuration and the repository settings.
- It computes a [Plumber Score](/blog/plumber-score-cicd-security-standard): every scan starts at 100 points, findings subtract by severity, and **a single Critical finding forces an E**.
- The scanner is open source, the [scoring algorithm](https://github.com/getplumber/plumber/blob/main/docs/scoring.md) is public, and every grade is per-project and verifiable.
- **The dataset is [Plumber Radar](/radar) itself.** Every number in this article is an aggregate over the public dashboard: each project behind it is a row you can open, with its grade and findings.

This is not a survey of what teams say they do. It is what their repositories actually contain. Full cohort-selection details and caveats are in the [methodology](#study-metadata).

## CI/CD is still a blind spot

Application code gets reviewed. Dependencies get scanned. The pipeline that builds and ships both gets neither.

- **It belongs to nobody in particular.** Pipeline security sits between the platform team and the security team, and is rarely anyone's explicit job.
- **2,863 repositories have no CI at all** and still surfaced with findings, because governance risk like an unprotected branch exists with or without a pipeline.
- **Even the best cohort is not clean.** Half the A-graded projects still carry one open finding.
- **Offense is already automated.** The [hackerbot-claw campaign](/blog/hackerbot-claw-cicd-governance) compromised 5 of 7 targeted repositories using nothing but misconfigurations documented for years.

## Where the risk actually sits

Pipeline risk is not one problem. It concentrates in a handful of recurring patterns, and the same ones show up again and again across the whole cohort.

<Image src={chartRisks} alt="Share of 15k+ public projects exposed to each risk: unpinned or mutable dependencies 55%, over-broad or undeclared permissions 54%, unprotected default branch 49%, untrusted third-party sources 48%, injection and poisoning paths 15%, unmaintained or vulnerable dependencies 10%, secret over-exposure 5%, unverified remote code execution 4%, privileged container execution 1%" width={780} densities={[1, 2]} quality={92} class="mx-auto rounded-xl" />

<div class="my-6 grid gap-3 sm:grid-cols-2">
  <div class="border-border/50 rounded-lg border p-4">
    <strong class="text-foreground">Unpinned or mutable dependencies</strong>
    <p class="text-foreground/60 mt-1 text-sm">A tag or branch can be moved under you. The code you reviewed is not the code that runs tomorrow.</p>
  </div>
  <div class="border-border/50 rounded-lg border p-4">
    <strong class="text-foreground">Over-broad or undeclared permissions</strong>
    <p class="text-foreground/60 mt-1 text-sm">Default tokens can push code, publish packages and edit releases. Most pipelines never narrow them.</p>
  </div>
  <div class="border-border/50 rounded-lg border p-4">
    <strong class="text-foreground">Unprotected default branch</strong>
    <p class="text-foreground/60 mt-1 text-sm">The branch releases ship from accepts force pushes, or merges with no review required.</p>
  </div>
  <div class="border-border/50 rounded-lg border p-4">
    <strong class="text-foreground">Untrusted third-party sources</strong>
    <p class="text-foreground/60 mt-1 text-sm">Third-party code and images pulled from outside any trust policy, running with full access to the job.</p>
  </div>
  <div class="border-border/50 rounded-lg border p-4">
    <strong class="text-foreground">Injection and poisoning paths</strong>
    <p class="text-foreground/60 mt-1 text-sm">Attacker-controlled text reaching a shell, or a build cache an outsider can write into.</p>
  </div>
  <div class="border-border/50 rounded-lg border p-4">
    <strong class="text-foreground">Unmaintained or vulnerable dependencies</strong>
    <p class="text-foreground/60 mt-1 text-sm">Archived actions, published CVEs, and commits impersonating a trusted author.</p>
  </div>
  <div class="border-border/50 rounded-lg border p-4">
    <strong class="text-foreground">Secret over-exposure</strong>
    <p class="text-foreground/60 mt-1 text-sm">Entire secret contexts handed to workflows, or debug tracing that prints them into logs.</p>
  </div>
  <div class="border-border/50 rounded-lg border p-4">
    <strong class="text-foreground">Unverified remote code execution</strong>
    <p class="text-foreground/60 mt-1 text-sm"><code>curl</code> piped straight into a shell. The <a href="/blog/shai-hulud">Shai-Hulud</a> propagation pattern, still alive.</p>
  </div>
</div>

The top four are the dangerous ones, because they combine. An unpinned action, pulled from an untrusted source, running with default write permissions, on a branch nobody protects: that is the exact shape of the [tj-actions/changed-files compromise](/blog/tj-actions-compromised).

## Popularity is not protection

The comfortable assumption is that widely-used projects earn their trust: more eyes, more maintainers, better hygiene. The data says otherwise.

<Image src={chartStars} alt="Share of GitHub projects graded D or E by star count: 80% for projects above 10k stars, 81% for 1k to 10k, 48% for 100 to 1k, and 68% under 100 stars" width={780} densities={[1, 2]} quality={92} class="mx-auto rounded-xl" />

- **Above 10k stars, 80% grade D or E** and 52% carry a Critical finding.
- **The healthiest band is the unglamorous middle** (100 to 1k stars): 48% D or E, and 22% earn an A.
- When you adopt a popular action or library, you inherit its pipeline, not its stars: the unpinned dependencies it builds with, the permissions its workflows run with. **Stars measure adoption, not the thing that gets you compromised.**

Nothing on that list needs a security team or a budget. For most projects it is an afternoon of configuration.

## Grade your own pipeline

1. **Get your grade.** Install the [Plumber CLI](https://github.com/getplumber/plumber) (`brew install getplumber/plumber/plumber`) and run `plumber analyze`. The grade appears immediately, and `--score-point` shows where every point went.
2. **Publish it.** Add `score-push: true` (GitHub) or `score_push: true` (GitLab) to get a verifiable [score page](/docs/plumber-score).
3. **Check your dependencies.** Look them up at `score.getplumber.io/<host>/<owner>/<repo>`, or browse the live cohort on [Plumber Radar](/radar).

If your grade comes back a D or an E, you are in the majority. The difference is that now you know, and the fix list is short.

<Aside variant="caution" title="Key takeaways">

1. **91% of public projects carry a High or Critical risk** right now, and 54% carry a Critical one.
2. **68% grade E, 76% grade D or E**, and the average is a D. Only 3% are clean.
3. **The risk concentrates in four patterns**: unpinned dependencies, over-broad permissions, unprotected branches, untrusted sources. They combine into real attack paths.
4. **Popularity is not protection**: 80% of GitHub projects above 10k stars grade D or E. Check a dependency's score, not its stars.
5. **CI/CD is a blind spot**: governance risk exists even without a pipeline, and it is rarely anyone's explicit job.
6. **All of it is configuration.** No zero-days required, to attack it or to fix it.

</Aside>

## FAQ

<div class="my-4 space-y-2">

<details>
<summary>What is the state of CI/CD security in 2026?</summary>

Measurably poor. Across 15k+ public GitHub and GitLab projects graded by Plumber Radar in July 2026, 68% score E (the worst grade, reserved for Critical findings), 76% score D or E, and the average is a D. 91% carry a High or Critical finding, and 54% carry a Critical one.

</details>

<details>
<summary>How were the pipelines graded?</summary>

With the open-source Plumber CLI, which reads each project's pipeline configuration (`.gitlab-ci.yml`, `.github/workflows/*.yml`) and repository settings, evaluates them against pipeline-security and governance controls, and computes an A to E Plumber Score. Every scan starts at 100 points, findings subtract by severity, and one Critical finding forces an E. The scanner and the [scoring specification](https://github.com/getplumber/plumber/blob/main/docs/scoring.md) are open source, and every grade is public on [Plumber Radar](/radar).

</details>

<details>
<summary>What are the most common CI/CD security risks?</summary>

Four dominate: unpinned or mutable dependencies (55% of projects), over-broad or undeclared permissions (54%), unprotected default branches (49%), and untrusted third-party sources (48%). Behind them sit injection and cache-poisoning paths (15%), unmaintained or vulnerable dependencies (10%), secret over-exposure (5%) and unverified remote scripts (4%).

</details>

<details>
<summary>Why do popular projects score worse?</summary>

Among GitHub projects with more than 10k stars, 80% grade D or E and 52% carry a Critical finding, worse than mid-size projects (the 100 to 1k star band is the healthiest, with 22% earning an A). Large projects accumulate more workflows, more third-party actions and more legacy configuration, and pipeline security is rarely anyone's explicit responsibility. Stars measure adoption, not the safety of the pipeline that ships the code.

</details>

<details>
<summary>Why is CI/CD a blind spot?</summary>

Application code is reviewed and dependencies are scanned, but the pipeline that builds and ships them usually belongs to nobody in particular. Governance risk exists even without a pipeline: 2,863 repositories in the cohort have no CI at all and still surfaced with findings such as an unprotected default branch.

</details>

<details>
<summary>Is any of this hard to fix?</summary>

No. Every risk measured here lives in configuration files and repository settings. Pinning dependencies, declaring permission scopes, protecting the default branch and dropping privileged escape hatches is typically an afternoon of work, with no application code changes.

</details>

<details>
<summary>How do I check my own project's grade?</summary>

Run `plumber analyze` from your repository with the free, open-source [Plumber CLI](https://github.com/getplumber/plumber); the grade appears in the terminal immediately. Add `score-push: true` (GitHub) or `score_push: true` (GitLab) to your CI to publish a score page at `score.getplumber.io/<host>/<owner>/<repo>` that anyone can verify.

</details>

<details>
<summary>Can I verify or reproduce these numbers?</summary>

Yes. The headline statistics come from the live [Plumber Radar](/radar) dashboard, which is public and refreshed continuously, so current figures will drift from this July 2026 snapshot as projects change. The scanner, the scoring algorithm, and every per-project grade are public, so any number can be re-derived by running the CLI against the same repository.

</details>

<Aside variant="info" title="Study metadata">
- Snapshot: July 20, 2026 &#183; public projects on github.com and gitlab.com
- Source dataset: the live **[Plumber Radar](/radar)** dashboard. Every aggregate in this article can be re-derived from it, and every project behind the numbers is a public row with its grade and findings

- Risk categories group the equivalent controls from both platforms (for example "unpinned or mutable dependencies" covers unpinned actions and mutable container image tags), and are measured as the share of the whole cohort exposed to at least one control in the category
- Pipeline risks are measured on projects that have a pipeline; governance risks such as branch protection are measured on every repository, including those without CI
- Scanner: Plumber CLI `v0.4.8`, default policy
- Branch protection is only measurable on GitHub in this scan
