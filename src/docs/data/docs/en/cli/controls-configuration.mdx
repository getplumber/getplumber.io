The field-by-field reference for the `gitlab.controls:` and `github.controls:` sections of `.plumber.yaml`. Use the [index](#controls-index) to jump to a control. For the three ways to write the file see [Configuration](/docs/cli/configuration); for what each issue means and how to fix it, [Issues](/docs/cli/issues).

<Aside variant="info" title="Reading the tables">
  **Default** is the value in the `plumber:default` baseline: what runs with no `.plumber.yaml`, what an overlay inherits, and what `plumber config generate` writes (Plumber v0.5.10). Where the CLI behaves differently when a key is simply omitted from a full configuration, that fallback is given as *unset*. Long baseline lists are shown in the YAML block under each table rather than in the table itself. Every YAML block is nested the way the file is, so it pastes into `.plumber.yaml` as it is. The `CTRL-nnn` on each control is the id the Platform's Policies page shows.
</Aside>

## How a control block works

### Where a block lives

Every control is a block under `gitlab.controls.<name>` or `github.controls.<name>` in a schema `version: "2.0"` file. The block name is the name you pass to `--controls` and `--skip-controls`, and the `controlName` of its findings in the JSON report.

### Turning a control on or off

Every block accepts `enabled: true | false`. What a missing block means depends on the mode:

| Mode | Missing block |
|---|---|
| [Overlay](/docs/cli/configuration#extended-configuration-recommended) (`extends: plumber:default`) | Inherits the baseline block |
| [Full configuration](/docs/cli/configuration#full-configuration) (no `extends`) | The control does not run |

A control that is off or absent is reported as `skipped`, never as passed.

### Overlays: lists replace, maps merge

In an overlay, nested maps merge key by key, but a list you write replaces the baseline list entirely. Writing `tags: [nightly]` under `containerImageMustNotUseForbiddenTags` drops `latest`, `dev` and the other baseline tags, so repeat the entries you want to keep.

The two curated allowlists are the exception. `containerImageMustComeFromAuthorizedSources` (`trustedUrls`) and `githubActionMustComeFromAuthorizedSources` (`trustedGithubActions`) carry an `includePlumberDefaults` switch: with the default `true`, your entries are added to Plumber's curated list; with `false`, only your entries are trusted. The switch only acts in overlay mode. `plumber config resolve` prints the final list.

### Fields you leave unset

Fields that describe the setting a project must have (`allowForcePush`, `codeOwnerApprovalRequired`, every field of the merge request settings controls) are only compared when you set them. Leaving one out asserts nothing about it, and there is no way to expect the unsafe value.

A few booleans are `true` when omitted from a full configuration. Every other omitted boolean is `false`.

| Field | Control |
|---|---|
| `detectInsecureDaemon` | `pipelineMustNotUseDockerInDocker` |
| `defaultBranchIsForbiddenVersion` | `includesMustNotUseForbiddenVersions` |
| `includePlumberDefaults` | both allowlist controls |
| `trustGithubOfficialActions`, `trustSameOrgActions` | `githubActionMustComeFromAuthorizedSources` |
| `trustSameGroupComponents`, `trustSameInstanceComponents`, `trustGitlabOfficialComponents` | `componentMustComeFromAuthorizedSources` |
| `trustSameGroupFunctions` | `functionMustComeFromAuthorizedSources` |
| `allowFailureMustBeFalse.enabled`, `rulesMustNotBeRedefined.enabled`, `whenMustNotBeManual.enabled` | `securityJobsMustNotBeWeakened` |

### Controls that need configuration

Some controls assert nothing until they are given something to check: a list of tags, a set of required components, a minimum number of approvals. They carry a <Badge text="Needs configuration" variant="caution" /> badge below. In an overlay the baseline supplies that configuration; in a full configuration, `enabled: true` alone makes the control run and pass with nothing to check.

### Required expressions

The three "must include" controls (`pipelineMustIncludeComponent`, `pipelineMustIncludeTemplate`, `workflowMustIncludeRequiredActions`) take their requirement in one of two equivalent forms, never both.

- `required`: a boolean expression with `AND`, `OR` and parentheses. `AND` binds tighter than `OR`, so `a AND b OR c` reads `(a AND b) OR c`.
- `requiredGroups`: the same logic as a list of lists. The outer list is an OR, each inner list is an AND.

```yaml
# These two are equivalent
required: (templates/go/go AND templates/trivy/trivy) OR templates/full-go-pipeline
requiredGroups:
  - ["templates/go/go", "templates/trivy/trivy"]
  - ["templates/full-go-pipeline"]
```

### What is fixed

- **Severity.** Each issue code carries its own severity (see [Issues](/docs/cli/issues)); in a report, a finding on an [attack path](/docs/cli/how-the-analysis-works#4-attack-paths) shows the path's tier instead. Configuration decides whether a control runs and what it checks, not how a finding is graded.
- **GitLab plan tiers.** Controls and fields that read a setting only a paid plan exposes carry a <Badge text="GitLab Premium" variant="note" /> or <Badge text="GitLab Ultimate" variant="note" /> badge. On GitLab Free, enable only what your plan exposes.
- **Validation.** Unknown control names and fields produce a warning with a "did you mean" suggestion and are ignored. `plumber config validate` reports them without a scan; `plumber analyze --fail-warnings` turns them into a failure.

## Controls on both providers

One block definition, under `gitlab.controls` and under `github.controls`. Where a default differs between providers, both are given.

### containerImageMustNotUseForbiddenTags

<div class="not-content mt-1 mb-5 flex flex-wrap items-center gap-1.5">
  <Badge text="CTRL-102" variant="info" />
  <Badge text="On by default" variant="tip" />
  <Badge text="Needs configuration" variant="caution" />
</div>

Flags container images referenced by a mutable tag and, when digest pinning is required, any image not pinned by digest. Raises [ISSUE-102](/docs/use-plumber/issues/ISSUE-102) (medium) and [ISSUE-103](/docs/use-plumber/issues/ISSUE-103) (high).

| Field | Default | Description |
|---|---|---|
| `enabled` | `true` | Turns the control on. |
| `tags` | 6 tags, see below | Tags considered mutable and therefore forbidden. |
| `containerImagesMustBePinnedByDigest` | `true` (unset: `false`) | Requires every image to be referenced by an immutable `@sha256:` digest. Takes precedence over `tags`: a version tag such as `alpine:3.19` is then also flagged. |
| `exemptImages` | empty | Images that neither ISSUE-102 nor ISSUE-103 checks while they use one of the `tags`. See [Exempting an image](#exempting-an-image). |

```yaml
      tags: [latest, dev, development, staging, main, master]
```

#### Exempting an image

Some images are only published on a mutable tag, for example an internal tool released as `:latest` only. Rather than turning the whole control off, list them in `exemptImages`.

An image is exempt from both ISSUE-102 and ISSUE-103 when its registry and name match an entry **and** its tag is one of the `tags`. Its digest plays no part. Any other tag of the same image is still checked. With the configuration below:

| Image | Result |
|---|---|
| `ghcr.io/my-org/report-tool:latest` | Exempt |
| `ghcr.io/my-org/report-tool:latest@sha256:…` | Exempt: the digest is ignored |
| `ghcr.io/my-org/report-tool:v1.0.2` | Not exempt: `v1.0.2` is not a forbidden tag, so ISSUE-103 is raised |
| `debian:latest`, `docker.io/library/debian:latest` | Exempt |
| `public.ecr.aws/docker/library/debian:latest` | Not exempt: another registry |

```yaml
github:
  controls:
    containerImageMustNotUseForbiddenTags:
      enabled: true
      tags: [latest, dev, development, staging, main, master]
      containerImagesMustBePinnedByDigest: true
      exemptImages:
        - ghcr.io/my-org/report-tool
        - debian
        - "quay.io/my-org/*"
```

- **No tag in the entries.** An entry is a registry and an image name. Which tags are accepted comes from `tags`.
- **Docker Hub spellings match each other.** `debian`, `library/debian`, `docker.io/debian` and `docker.io/library/debian` name the same image, in the entry and in the pipeline alike. A namespace still counts, so `redis` does not match `redis/redis-stack-server`.
- **Globs.** `*` matches any characters, slashes included: `quay.io/my-org/*` covers every image of that namespace, and `*/busybox` covers `busybox` on any registry. Quote an entry that starts with `*`.
- **Variables.** `$REGISTRY/tool` and `${REGISTRY}/tool` match each other. The variable is compared by name, not expanded.
- **One block per provider.** The list is read from the block of the provider being analyzed. An entry under `gitlab.controls` has no effect on a GitHub analysis.
- **Exempt images stay visible.** The report lists them under *Exempted by configuration*, and they are not counted as unpinned.

### branchMustBeProtected

<div class="not-content mt-1 mb-5 flex flex-wrap items-center gap-1.5">
  <Badge text="CTRL-501" variant="info" />
  <Badge text="On by default" variant="tip" />
  <Badge text="Needs configuration" variant="caution" />
  <Badge text="Needs an API token" variant="note" />
</div>

Checks that the branches matching `namePatterns` (and the default branch) are protected, and that their protection meets the expectations you set. Raises [ISSUE-501](/docs/use-plumber/issues/ISSUE-501) (critical) when a branch is not protected and [ISSUE-505](/docs/use-plumber/issues/ISSUE-505) (high) when its settings are not compliant. Without a token the control abstains. On GitHub it reads both classic branch protection and rulesets, and evaluates the stricter of the two.

| Field | Default | Description |
|---|---|---|
| `enabled` | `true` | Turns the control on. |
| `defaultMustBeProtected` | `true` | Also requires the default branch to be protected, whether or not it matches `namePatterns`. |
| `namePatterns` | 5 patterns, see below | Branch name patterns that must be protected. Wildcards are supported. |
| `allowForcePush` | `false` | Expectation: `false` requires force push to be disabled. |
| `codeOwnerApprovalRequired` | `false` | Expectation: `true` requires code owner approval. <Badge text="GitLab Premium" variant="note" /> |
| `minMergeAccessLevel` | GitLab `30`, GitHub unset | Expectation: the minimum access level allowed to merge. GitLab only. |
| `minPushAccessLevel` | GitLab `40`, GitHub unset | Expectation: the minimum access level allowed to push. GitLab only. |

GitLab access levels: `0` No one (the strictest), `30` Developer, `40` Maintainer.

<Tabs defaultValue="gitlab" syncKey="provider">

```yaml
  controls:
    branchMustBeProtected:
      enabled: true
      defaultMustBeProtected: true
      namePatterns: [main, master, release/*, production, dev]
      allowForcePush: false
      codeOwnerApprovalRequired: false
      minMergeAccessLevel: 30
      minPushAccessLevel: 40
```

  </TabsContent>

```yaml
    branchMustBeProtected:
```

### tagMustBeProtected

<div class="not-content mt-1 mb-5 flex flex-wrap items-center gap-1.5">
  <Badge text="CTRL-510" variant="info" />
  <Badge text="On by default" variant="tip" />
  <Badge text="Needs an API token" variant="note" />
</div>

Checks that the release tag patterns in use are protected: tag updates and deletions blocked, and tag creation restricted. Raises [ISSUE-510](/docs/use-plumber/issues/ISSUE-510) (critical, or high when no pipeline or workflow runs on a tag). A pattern is only checked while it is in use: an existing tag matches it or, on GitHub, a workflow triggers on it. On GitLab it reads protected tags; on GitHub, active tag rulesets, the repository's own and the organization's. Without access the control reports "not evaluated" and raises no finding. On GitLab it is not evaluated in Platform mode yet.

| Field | Default | Description |
|---|---|---|
| `enabled` | `true` | Turns the control on. |
| `namePatterns` | `[v*]` | Tag name patterns that must be protected. Wildcards are supported. On GitHub, every `on.push.tags` pattern of a workflow is checked as well. |
| `requireCreationRestricted` | `true` | Expectation: `true` also requires tag creation to be restricted (GitLab: left to Maintainers or narrower; GitHub: **Restrict creations**). `false` checks updates and deletions only. |

### securityJobsMustNotBeWeakened

<div class="not-content mt-1 mb-5 flex flex-wrap items-center gap-1.5">
  <Badge text="CTRL-410" variant="info" />
  <Badge text="On by default" variant="tip" />
  <Badge text="Needs configuration" variant="caution" />

Flags security scanning jobs that are allowed to fail, whose rules were overridden to skip them, or that were made manual. Raises [ISSUE-410](/docs/use-plumber/issues/ISSUE-410) (critical). Only jobs matching `securityJobPatterns` are checked, and the control counts as skipped when all three sub-checks are off.

| Field | Default | Description |
|---|---|---|
| `enabled` | `true` | Turns the control on. |
| `securityJobPatterns` | per provider, see below | Job name patterns treated as security jobs. Wildcards are supported. On GitHub the pattern is matched against `<workflow file>/<job id>`, for example `codeql/analyze`. |
| `allowFailureMustBeFalse.enabled` | GitLab `false`, GitHub `true` | The job must not carry `allow_failure: true` (GitLab) or `continue-on-error: true` (GitHub). Off on GitLab because GitLab's own security templates ship with `allow_failure: true`. |
| `rulesMustNotBeRedefined.enabled` | `true` | The job's `rules:` must not be overridden to `when: never` or `when: manual`. |
| `whenMustNotBeManual.enabled` | `true` | The job must not be `when: manual` (GitLab) or reachable only through a manual dispatch trigger (GitHub). |

### pipelineMustNotUseDockerInDocker

<div class="not-content mt-1 mb-5 flex flex-wrap items-center gap-1.5">

Flags a job whose triggers include an event GitHub restricts to read-only cache access (`pull_request_target`, `issue_comment`, `workflow_run`, `discussion`...) and whose `cache-mode` is `write` or `write-only`, set on the job or inherited from its workflow. Code running in such a job can write caches every default-branch run restores. Raises [ISSUE-705](/docs/use-plumber/issues/ISSUE-705?p=github) (high). `push`, `workflow_dispatch`, `repository_dispatch`, `delete`, `registry_package`, `page_build`, `schedule`, `pull_request` and its review events, `release` and `merge_group` are safe triggers, and a job without `cache-mode` is silent.

| Field | Default | Description |
|---|---|---|
| `enabled` | `true` | Turns the control on. |
| `exemptWorkflows` | empty | A list of globs on the workflow file name, such as `triage.yml`; every job of a matching workflow is exempt. |
| `exemptJobs` | empty | A list of globs on `<workflow>/<job id>`, such as `triage/label`; a matching job is exempt. |

An exemption accepts the risk: the check skips the job, and the output lists every exempted job it would have flagged under **Exempted by configuration**, so the exemption stays visible.

```yaml
github:
  controls:
    untrustedTriggersMustNotWriteCache:
      enabled: true
      exemptWorkflows: []
      exemptJobs: []
        # - 'bot/warm-cache'
```

<Aside variant="info">
  This control replaces `releaseWorkflowsMustNotRestoreUntrustedCache`, which flagged release jobs restoring a cache not scoped to the release ref. A configuration that still uses the old key is ignored with a warning: run `plumber config migrate` to rename it. `publishActions`, `cacheActions`, `publishScriptPatterns`, `publishScriptExcludePatterns` and `allowedJobs` are gone; list the jobs you accept under `exemptJobs`.
</Aside>

### workflowsMustBeValid

<div class="not-content mt-1 mb-5 flex flex-wrap items-center gap-1.5">
  <Badge text="CTRL-423" variant="info" />
  <Badge text="On by default" variant="tip" />
</div>

Flags a file under `.github/workflows` that cannot be parsed as a workflow (an undefined YAML anchor, a duplicate key, a tab-indented block, a syntax error), which GitHub shows as an invalid workflow and never runs. The other workflow files are analyzed and scored as usual; when every file is invalid, the controls that read the workflows show as not evaluated. Only YAML parse failures are reported: a well-formed file GitHub still rejects (a job without `runs-on`, say) is left to the Actions tab or actionlint. Duplicate keys are compared ignoring case, as GitHub does. Raises [ISSUE-423](/docs/use-plumber/issues/ISSUE-423?p=github) (low). No field beyond `enabled`. When the control is off, or absent from a [full configuration](/docs/cli/configuration#full-configuration) without `extends`, the control shows as `skipped`, but an invalid file is not dropped silently: it degrades the run and the score is withheld.

### workflowMustIncludeRequiredActions

<div class="not-content mt-1 mb-5 flex flex-wrap items-center gap-1.5">
  <Badge text="CTRL-417" variant="info" />
  <Badge text="Off by default" variant="note" />
  <Badge text="Needs configuration" variant="caution" />
</div>

Checks that the workflows of the repository, taken together, reference the required actions or reusable workflows. Raises [ISSUE-417](/docs/use-plumber/issues/ISSUE-417?p=github) (high).

| Field | Default | Description |
|---|---|---|
| `enabled` | `false` | Turns the control on. |
| `required` | unset | The requirement as a boolean expression of `owner/repo` or `owner/repo/path` entries, matched without regard to the `@ref`: `myorg/sast-scan` matches `myorg/sast-scan@v2` and `myorg/sast-scan/sub@abc123`. Exclusive with `requiredGroups`. |
| `requiredGroups` | empty | The same requirement as a list of lists (an OR of ANDs). Exclusive with `required`. |

```yaml
github:
  controls:
    workflowMustIncludeRequiredActions:
      enabled: true
      required: myorg/sast-scan AND myorg/policy/.github/workflows/scan.yml
```
