## What is a Plumber Score?

Plumber Score is a single **A-E** grade for your CI/CD security. The open-source
[Plumber CLI](https://github.com/getplumber/plumber) produces it on **every
run**, locally or in your CI pipeline. The score is **contextual**: Plumber
assembles its findings into [attack paths](/docs/cli/how-the-analysis-works#4-attack-paths) and grades the
worst realistic consequences, not a flat count of findings. Only what Plumber can
prove moves the grade: a fact it had to assume or could not read is shown in the
report, never priced.

| Grade | Points | What it means |
|:-----:|:------:|---------------|
| <span class="font-bold text-primary-400 dark:text-primary-300">A</span> | ≥ 90 | **Excellent**: no significant exposure found |
| <span class="font-bold text-primary-400 dark:text-primary-300">B</span> | 71 – 89 | **Good**: minor exposure |
| <span class="font-bold text-yellow-500 dark:text-yellow-400">C</span> | 51 – 70 | **Moderate**: exposure worth fixing |
| <span class="font-bold text-orange-500 dark:text-orange-400">D</span> | 31 – 50 | **Poor**: significant accumulated exposure |
| <span class="font-bold text-red-400 dark:text-red-300">E</span> | < 31 | **Critical**: a Critical attack path remains, or heavy accumulated losses |

A grade from A to D says nothing about the number of paths. An **E needs a
Critical item**: a Critical attack path keeps the score at 30 points or below.
How Plumber gets from your files to the grade, and how the points add up, is on
[How the analysis works](/docs/cli/how-the-analysis-works).

## Publish your score

A CI run can publish your score to `score.getplumber.io`, where it becomes a live
badge for your repo.

Publishing is **opt-in** and never sends your source code: once enabled, Plumber sends its
analysis JSON output to `score.getplumber.io` after each run. Every run that has score push
enabled publishes its result for its branch. The public badge and the project's score follow
the default branch only: a merge-request or pull-request run is stored under its branch and
never changes the badge.

<Aside variant="info" title="A few things to keep in mind">
- All published scores are public
- The score always reflects the latest analysis on your default branch
- Publishing never fails your pipeline: if the push doesn't go through, your analysis still succeeds
</Aside>


### <Icon name="tabler/brand-github" class="inline-block size-[1em] self-center shrink-0" /> How to publish with GitHub

1. Add the [GitHub Action](/docs/cli/github#run-with-github-actions) to your workflow
with the correct workflow `permissions` and `score-push` enabled in the action
    ```yaml
    permissions:
      contents: read
      security-events: write
      id-token: write
    jobs:
      plumber:
        steps:
          - uses: getplumber/plumber@d1133cdac48cfdf0c0004637ae4af38bcf9f16c7 # pinned plumber version: v0.7.11
            with:
              score-push: true
    ```
2. Add a badge in your `README.md` (replace `OWNER` and `REPO`)
    ```md
    [![Plumber Score](https://score.getplumber.io/github.com/OWNER/REPO.svg)](https://score.getplumber.io/github.com/OWNER/REPO)
    ```


### <Icon name="tabler/brand-gitlab" class="inline-block size-[1em] self-center shrink-0" /> How to publish with GitLab

1. Add the [GitLab CI component](/docs/cli/gitlab#run-with-the-gitlab-ci-component) to your
`.gitlab-ci.yml` with the `score_push` input enabled
    ```yaml
    include:
      - component: gitlab.com/getplumber/plumber/plumber@f97e0377cdc54f51eeb75f817f458cb9af0a4db1 # pinned plumber version: v0.7.11
        inputs:
          score_push: true
    ```
2. Add a badge in your repo: **Settings → General → Badges**
    - **Link**: `https://score.getplumber.io/gitlab.com/%{project_path}`
    - **Badge image URL**: `https://score.getplumber.io/gitlab.com/%{project_path}.svg`

## Gate your CI on the score

The score is what passes or fails a `plumber analyze` run (exit code 1 on
failure).

- `--min-score <A-E>` is the main gate: the run fails when the letter is below
  the one you set. `--min-score B` fails on C, D, E.
- `--min-points <0-100>` is the fine-grained variant for gating on exact
  points. Without any flag, the default is **100 points**: any finding fails.
- Set both and both must pass.

```bash
plumber analyze --min-score B
```

The same gate is available as `min-score` / `min-points` inputs on the
[GitHub Action](/docs/cli/github#all-inputs) and `min_score` / `min_points` on
the [GitLab component](/docs/cli/gitlab). The legacy `--threshold` flag
(percentage of passing controls) is deprecated: it still works with a warning,
and its old default is equivalent to the default score gate.
